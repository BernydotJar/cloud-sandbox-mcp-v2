6. POR QUÉ FALLABAN LOS INTENTOS ANTERIORES

a) Homebrew retiró el ejecutable Node 26.5.0 mientras launchd aún lo referenciaba.
   Se migraron los dos servicios a la ruta opt estable, se repararon sondas
   vivas y el usuario habilitó el nuevo ejecutable en Accesibilidad.

b) Captura completa no implica control AX/DOM. Se reparó captura, pero no era
   prueba de que se pudiera editar el compositor.

c) En Teams real AXSetValue y AXSelectedText fueron aceptados sin cambiar texto.
   Se descartaron como solución del compositor. La ruta process_unicode sigue
   limitada por el PID compartido entre ventanas Edge: no sustituye DOM seguro
   cuando el usuario trabaja en otra ventana de ese mismo proceso.

d) El primer DOM execCommand produjo input confiable, pero CKEditor descartó el
   cambio; el compositor siguió vacío y la recarga también quedó vacía.
   No se aceptó dispatched=true como guardado.

e) Teams usa CKEditor 5. Se observó data-tid=ckeditor y ckeditorInstance real.
   La solución usa la API documentada:
     editableElement.ckeditorInstance.setData(escapedPlainTextAsParagraph)
   Comprueba raíz exacta, readonly, nodo, URL completa, título y huella actual.
   No llama focus en la ruta CKEditor, ni escribe textContent como sustituto.
   Valores se devuelven solo como vacío o SHA256/longitud. No permite sustituir
   un compositor rico no vacío por otro texto no vacío.

f) El bridge inicialmente interceptaba todo descubrimiento Edge para Teams.
   Se corrigió para conservar otros orígenes. Ver sección siguiente.
